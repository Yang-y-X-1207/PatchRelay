# 问题三：模型幻觉——成因与解决方案

## 什么是幻觉

模型输出了与事实不符的内容，且通常以高置信度表述。

幻觉不只是"编造事实"，还包括：
- 声称自己没有某个工具（工具内省失败）
- 编造不存在的 API / 文档 / 引用
- 用错误的推理得出看似合理的结论
- 忽略 context 中已有的信息，从训练记忆里"凭空"回答

---

## 幻觉的三个来源

所有幻觉都可以归入以下三个根源，解法要对症：

```
来源 A：参数化知识缺失
        模型根本不知道这件事，只好猜测或用相近的知识填充

来源 B：上下文注意力失焦
        答案就在 context 里，但模型没读到或读错了

来源 C：推理路径错误
        模型有信息，但推理过程走偏，得出了错误结论
```

> PatchRelay 案例属于 **来源 B**：工具 schema 在 context 里，
> 但自由文本生成路径对该区域的注意力不稳定。

---

## 解决方案（按成本从低到高）

---

### 第一层：提示工程（Prompt Engineering）成本：极低

**1. 要求"不确定就说不知道"**

```
"如果你不确定，请明确说'我不知道'，不要猜测。"
```

对来源 A 有效。打破模型"必须给出答案"的默认倾向。

**2. 要求说明依据**

```
"回答时，请引用你依据的具体信息（来自上下文哪段话，或你的训练知识）。"
```

一旦要求引用，无法引用的内容就不敢瞎说。对来源 A、B 有效。

**3. 思维链（Chain-of-Thought）**

```
"请一步一步思考，再给出答案。"
```

推理链暴露在外，错误更容易被发现或在中途被自我纠正。对来源 C 效果最好。

**4. 负面强制指令**

针对已知的幻觉模式，直接在 prompt 里封堵：

```
"工具一定存在，不要声称自己没有该工具，直接调用。"
```

这就是强化 SKILL.md 的本质：用规则覆盖模型的错误倾向。对来源 B 有效。

---

### 第二层：上下文接地（Grounding）成本：低

**核心思想：不让模型依赖记忆，把权威答案直接塞进 context。**

**RAG（检索增强生成）**

```
用户提问 → 先检索知识库，取出最相关文档
         → 文档注入 context
         → 模型基于文档回答，而非凭记忆
```

把"模型记得 X"变成"文档里说 X"，可验证，可追溯。对来源 A 效果最好。

**实时工具调用代替记忆**

```
❌ "现在 PatchRelay 的任务状态是什么？" → 模型凭记忆猜 → 可能幻觉
✅ 调用 patchrelay_get_task() 取值 → 把结果给模型 → 准确，无幻觉
```

凡是需要**实时、精确**数据的问题，都应设计成"工具调用取值"而非"让模型回忆"。

---

### 第三层：输出验证（Output Verification）成本：中

**自一致性（Self-Consistency）**

同一问题用不同措辞问多次，比较答案是否一致。不一致处为幻觉高风险区。

**链式核查（Chain-of-Verification, CoVe）**

```
步骤一：让模型给出初步答案
步骤二：让模型针对自己的答案，生成一组核查问题
步骤三：让模型逐一回答核查问题
步骤四：根据核查结果修正原答案
```

**独立验证模型**

用另一个模型（或同一模型的独立 session）核查原答案是否合理。

以上方法对来源 C（推理走偏）效果最好。

---

### 第四层：模型选择与配置成本：中

**换推理能力更强的模型**

Flash/lite 模型的校准（calibration）较差——不确定时也会给出高置信度答案。
Pro/Full 模型经过更多 RLHF 训练，倾向于"不确定时说不确定"，
工具选用和上下文遵循能力也更强。

**开启 Thinking / Reasoning 模式**

DeepSeek-R1、o1、Claude 开启 thinking 后，在生成最终答案前先做内部推理链，
大幅降低推理类幻觉（来源 C），也对工具主动选用判断有帮助。

**调低 Temperature**

对需要准确性的场景（工具调用、数据提取），Temperature 调至 0–0.3，
减少模型输出的随机性。

---

### 第五层：架构设计成本：高，但根本性

**工具调用代替记忆检索**

| 方式 | 示例 | 幻觉风险 |
|------|------|---------|
| 让模型记忆 | "现在大约有几个任务？" | 高 |
| 工具调用取值 | `patchrelay_get_task()` → `{"count": 3}` | 无 |

**结构化输出约束**

强制 JSON Schema 输出，格式以外的内容无处容身，幻觉空间被压缩。

**人在回路（Human-in-the-loop）**

高风险决策不直接执行，先输出给人审核再落地。

**微调（Fine-tuning）**

用领域内高质量问答对微调，把正确知识烧进权重，从根源解决来源 A。
适用于知识量大、context 放不下的私有领域场景。

> ⚠️ 注意：微调成本极高，只在前四层均不够用时才考虑。
> 对于"教模型用一个新工具"这类场景，写好 SKILL.md 就够，不需要微调。

---

## 汇总对照表

| 幻觉类型 | 根源 | 优先解法 |
|---------|------|---------|
| 模型不知道某件事 | 来源 A | RAG 接地 → 微调 |
| 模型没读 context（如工具内省）| 来源 B | 强制指令 → 换更强模型 → 开 Thinking |
| 模型推理走偏 | 来源 C | CoT → CoVe → Thinking 模式 |
| 需要实时 / 精确数据 | 来源 A+B | 工具调用接地，不依赖记忆 |
| 模型说"不知道"但还是猜 | 来源 A | Prompt 约束 + 降 Temperature |

---

## 通用原则

> **凡是能让模型"调用"代替"记忆"的地方，就用调用。**
> **凡是不得不靠记忆的地方，就用强约束 + 强模型。**
> **不要问模型"你有没有 X"，而是直接让它去做需要 X 的事。**
