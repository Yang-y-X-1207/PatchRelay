# 问题二：模型输出路径与知识来源

## 概述

理解 LLM 如何生成输出，需要从两个正交维度来看：
**输出形态**（模型吐出什么格式）和**知识来源**（模型从哪里找答案）。
两者组合决定了模型在每种情况下的表现质量。

---

## 维度一：输出形态

### 1. 自由文本生成

最基础的路径。模型逐 token 生成自然语言，无格式约束。

```
输入："PatchRelay 是什么？"
输出："PatchRelay 是一个本地执行中继……"
```

**特点：**
- 从训练记忆和 context 文字区召回内容
- 不会主动、系统性地遍历工具 schema 区
- 适合解释、描述、问答类任务
- 幻觉风险最高（模型可以"自由发挥"）

---

### 2. 工具调用（Function Calling）

模型判断需要调用工具时，输出结构化的 JSON 调用指令。

```json
{
  "name": "patchrelay_submit_task",
  "arguments": {
    "instruction": "给 README 加一节 Troubleshooting",
    "worker": "claude"
  }
}
```

**特点：**
- 主动查询注入的工具 schema 区，生成合法参数
- 执行完后将结果返回 context，再接文本生成路径汇报
- 这条路径上的幻觉极少（格式由 schema 约束）
- 需要模型"判断应该调用工具"才会触发

---

### 3. 结构化输出（Structured Output）

模型被约束为严格按 JSON Schema 输出，不允许 schema 外的任何内容。

```json
{ "status": "success", "task_id": "abc123", "worker": "claude" }
```

**特点：**
- 用于数据提取、表单填充，不触发外部执行
- 格式强约束，幻觉空间被大幅压缩
- 与工具调用的区别：只管输出格式，不触发外部动作

---

### 4. 推理 / 思考（Reasoning / Thinking Tokens）

部分模型（DeepSeek-R1、o1、Claude 开启 thinking）在生成最终答案前，
先在对用户不可见的草稿区做链式推理。

```
[thinking]  这个任务需要先分析依赖关系，再考虑测试覆盖……
[final]     推荐方案是……
```

**特点：**
- 思考 token 不计入对话上下文，不消耗可见 context
- 推理判断质量大幅提升（"该用哪个工具"这类决策题效果明显）
- 对工具主动选用和推理路径幻觉都有改善效果

---

## 维度二：知识来源

### A. 参数化知识（Parametric Knowledge）

存储在模型权重里，来自预训练。回答通用知识问题时主要用这个。

```
"Python 怎么写快排？" → 模型从权重里直接调取
```

- ✅ 无需查询，极快，不占 context
- ❌ 只有预训练见过的内容才有（自定义工具名不在其中）
- ❌ 知识存在截止日期

---

### B. 上下文检索（In-Context Retrieval）

从当前 context window 里读取：系统提示、对话历史、SKILL.md 注入的指令、工具 schema。

```
SKILL.md 写了 "编码任务必须调用 patchrelay_submit_task"
  → 模型读到这条指令
  → 本次 session 内"学会"用 patchrelay
```

- ✅ 可实时注入新知识，无需改模型权重
- ✅ 上下文学习（In-Context Learning）的核心机制
- ❌ 受 context 窗口上限限制
- ❌ 不同输出形态对 context 各区域的注意力分配不均

---

### C. 外部检索（RAG / Tool Results）

调用外部工具或检索系统，把结果塞回 context，再做文本生成。

```
用户问"当前任务状态" → 调用 patchrelay_get_task() → 结果进入 context → 模型解读
```

- ✅ 突破模型自身知识边界，获取实时、精确数据
- ✅ 用调用代替记忆，彻底规避参数化知识不足的问题
- ❌ 多一个调用环节，延迟增加

---

## 两个维度的交叉

|              | 参数化知识 | 上下文检索 | 外部检索 |
|--------------|-----------|-----------|---------|
| 自由文本生成  | ✅ 主力    | ⚠️ 不稳定  | —       |
| 工具调用      | ✅ 选工具  | ✅ 查 schema | ✅ 执行后取结果 |
| 结构化输出    | ✅         | —          | —       |
| 推理 / 思考   | ✅ 主力    | ✅ 更充分  | —       |

> **⚠️ 标注的格子 = 上下文检索 × 自由文本生成**
> 这正是 patchrelay 问题的落点：工具 schema 在 context 里，
> 但自由文本路径对 schema 区的注意力不稳定，导致幻觉。

---

## PatchRelay 问题的完整映射

```
场景                      输出形态        知识来源              结果
────────────────────────────────────────────────────────────────
问"你有哪些工具"          自由文本生成    参数化（无patchrelay）
                                        + 上下文（注意力弱）    ❌ 幻觉
                                        
指示"调用 patchrelay_*"  工具调用        上下文检索 schema 区   ✅ 正确执行

SKILL.md 写了强制指令     引导切换路径    上下文检索 skill 指令  ✅ 主动选用
```

---

## 核心结论

> **同一个模型、同一份配置、同一批工具，走不同路径就会有截然不同的表现。**
> 优化模型行为的关键，不是改工具注入方式，而是理解并引导模型走正确的路径。
>
> 实用原则：
> - 需要**精确数据** → 用工具调用代替文本生成
> - 需要**模型知道新事物** → 上下文注入（SKILL.md、系统提示）
> - 需要**复杂推理** → 开启 Thinking 模式
